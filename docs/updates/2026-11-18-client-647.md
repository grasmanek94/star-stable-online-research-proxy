# Client647 compatibility repair journal — 2026-11-18, version1.2.2

## Request and observed failure

The user reported that a Star Stable update broke hiding, then requested removal of version checks, recompilation, investigation of remaining problems and more update-tolerant AOBs. The loaded older1.2.0 proxy's log rejected F5 before scanning: `unsupported executable layout; expected645.348067`. The published1.2.1 source used the same old guard and address plan. The failure therefore did not establish that all signatures were broken; the header gate prevented that stage from running.

The current executable was copied read-only for analysis. Its file identity is647.349716 / Stellar647, SHA256 `62387b246a92a4874d20329caa6eaf06c7a29830263e94982a8bdad6b6110fe1`, preferred image base0x140000000, timestamp0x6AF719CF and SizeOfImage0x014C1000. These values document evidence only. No timestamp, version-string or exact image-size allowlist remains in activation. PE format/x64/section bounds still apply. The earlier645.348067 identity and addresses in historical journals are historical evidence, not current patch instructions.

An initial offline scan found9 of21 old AOB windows unique and12 absent. Even the9 retained windows now called moved helpers; globals and vtables also moved. Removing only the header gate would therefore remain insufficient. An intermediate gate-only rebuild passed isolated tests but was superseded by the complete repair and is not the final delivery.

## How the new paths were recovered

Opened a separate official IDA MCP headless database of the new executable and waited for analysis. No game process debugger or code writes were used. Old unique windows supplied surviving function anchors; native gate and helper xrefs located Character, rider, horse, pet, QuestControl, sale, collectible and viewport paths. Reviewed the surrounding instructions and pseudocode, rather than substituting an RVA delta. Changes are not one constant shift across the image.

The remote rider path calls its visibility helper at0x78A330. Its prologue takes the local-player safe-reference address with RIP-relative LEA and calls0x5F1EE0. That getter loads the registry global with RIP-relative MOV and conditionally tail-jumps to0x5FC760, the native safe-reference record resolver. The resolver decompilation/instructions retain index+12, generation+8,64-byte records, record generation+44 and object+32. Its full155-byte relocation-masked fingerprint is now validated before activation; a changed stride fails the regression test. The null/lazy-load behavior is observed game code, not a function the classifier calls.

Horse visibility at0x1E0FA0 takes horse+152, calls the same getter, and tail-jumps to the rider visibility helper when an owner resolves; otherwise it returns true. Enforce this getter/visibility relationship after decoding rel32 operands. Other shared target groups likewise must converge on one destination. The visual helper calls the discovered LOD helper. Target RVAs in JSON are fixture/reference values and are never compared with the live decoded destinations.

The new Character path retains all four LOD sites, the selective matrix-animation call and both floating-text sites. Rider/horse wrappers still receive RSI self; pet update uses RBX self while the original call's RCX is its owner. Character wrappers still classify RDI. Animation arguments still use the original skin-model register. Confirmed the existing MASM wrappers' register/return contracts remain suitable; no assembly behavior changes were required.

CPXParticleSystemEx's new entry at0x104E50 still begins with the complete5-byte instruction `48 89 5C 24 08` and has a179-byte window ending in E9 to child dispatcher0xAD050. Preserve exact stolen-instruction replay, entry+5 native continuation, and one native child dispatch on hiding. The legacy gate and detail-grass call also moved. Do not turn these into whole-subtree update skips. Particle resource/visual safety and actual savings still need live testing.

Primary vtables were recovered through MSVC RTTI class names and CompleteObjectLocator records, then checked against their virtual method entries. The checkpoint spelling is `CPXCheckPoint`, with a capital P; using `CPXCheckpoint` finds the wrong/nonexistent identity. Control bits and ancestry distinguish own actors; a class-name match alone must never determine local ownership.

## Runtime discovery and future compatibility

1. Validate a bounded Windows x64 PE structure. Use its section sizes for bounds; do not compare timestamp, product version or exact SizeOfImage with a known release.
2. Scan executable sections for each of21 unique ordered AOB windows. Masks cover rel32 CALL/JMP operands, short/near conditional-jump operands and RIP-relative address operands identified from decoded instructions. Keep instruction opcodes, register choices, field offsets and relevant constants fixed. Missing or multiple matches reject activation.
3. Decode E8 targets or the extended-particle final E9. Require executable destinations, shared-target consistency, relocation-masked helper fingerprints and the explicit horse/player/getter and visual/LOD relationships. Validate the native registry record resolver's code, including64-byte stride and generation/index/object offsets. AOB wildcarding is not permission to accept arbitrary functions.
4. Decode the two globals from the known helper/getter instruction positions. Require addresses and complete8/16-byte spans in readable writable non-executable image data. No hardcoded global RVA is installed into Config.
5. Scan readable, non-writable, non-executable image sections at pointer alignment for primary RTTI vtables. Candidate COL signature must be1, base/cd offsets0, self-RVA valid and type name an exact bounded match. Require a unique result per class and executable virtual methods0 and14. These checks replace the15 fixed vtable RVAs.
6. Validate current local ownership: registry span/64-byte alignment, safe-reference generations and actor self references, exact discovered player/horse vtables, control bit4 on both, player+1608 horse reference and horse+152 owner resolving back to the player. Discovery does not make this live heap check optional.
7. Save the complete observed windows, including wildcarded operands, and prepare cache/thunks. Existing paused-thread context, code ownership, write bounds, exception recovery and exact F6 restoration rules still apply. Restore saved live bytes, never the reference JSON's rel32 values. On later F5 reuse the prepared addresses only for the same module and recheck local ownership; entire saved contexts are still checked before each patch transaction.

This increases survival of address-only changes. A new compiler layout, register allocation, changed function bodies, class/RTTI removal, object offsets, branch meaning or actor lifecycle can still require repair. Some masks cover branch destinations and some helper proofs are prefixes; successful matching is evidence, not a proof that every future semantic change will be detected. Known parent/name/owner field layouts are not inferred afresh on every update. Do not claim universal update compatibility or crash-free gameplay.

Config remains368 bytes,14 categories and21 wrappers. Default8 still selects only remote horses/riders/pets; master starts off. Preset0 remains all filters. No ignore lists, chat, collision, obstacle logic, controls, loader entry contracts or category policy were changed. No new recurring scan occurs in the frame path: discovery is preparation work.

## Evidence and validation

`client-647-file-audit.json` records a successful native file audit using the production Discover implementation, not just a separately reimplemented pattern scanner. The optional command is:

```powershell
out/build/vs2026-x64/bin/Release/sso_runtime_tests.exe --inspect-client <path-to-SSOClient.exe>
```

The helper reads the provided file, validates/mapping its sections in private read/write memory, applies DIR64 base relocations for RTTI pointers and calls production discovery. It opens no game process, invokes no game function, does not set execute permission on copied game pages, does not allocate patch thunks, does not alter the file and never installs hooks. It reports21 patch/destination RVAs,2 global RVAs and15 exact RTTI identities. It deliberately does not claim that a live player exists. This mode is optional: no game file is needed for normal builds or CTest.

A current game process was no longer present when final build preparation continued, so no new live activation/visual result is claimed.

The native suite now covers27 scenarios. New regressions accept changed PE identity, shifted writable globals and all15 vtables, and a grass helper moved independently of its caller.
